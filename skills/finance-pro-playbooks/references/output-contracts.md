# User-Directed Delivery and Checks

Read when producing analysis or files. Delivery is judged against these written standards and applicable task checklists. No internal object, validation program, machine receipt or fixed visible template is required. Apply [completion-evidence.md](completion-evidence.md) for verification responsibilities and actual evidence.

## Request Priority

Use this order: explicit user requirements and latest corrections; supplied template or existing file; relevant task and format defaults; general Skill defaults. Preserve factual accuracy, model integrity, source traceability, confidentiality, capability boundaries and higher-priority instructions.

Keep the original request available while working. Record only relevant choices: data source and exclusivity, input version, formulas and metric labels, window, benchmark, annualization, assumptions, output format and file set, included/excluded content, preserved areas and corrections. Recheck the final response against those choices. Do not infer required output from an input filename or treat a negative clause as negating a separate positive task.

If the user changes scope, update affected notes and calculations before resuming. A correction is assessed against the original request and evidence; there is no fixed keyword parser that can overrule it.

## Visible Output

- Follow the requested language, headings, order, structure, length, detail and template. A table, short answer, file or custom medium does not require an extra report.
- Use the Playbook's professional medium and layout only when the user has not chosen them. Technical instructions for a specific medium apply when that medium is actually produced.
- An unlisted format is a tool-capability question. Use an appropriate creator and verifier; if unavailable, explain the limit and preserve the request rather than silently substituting another format.
- Distinguish facts, estimates, assumptions and conclusions. Keep material units, periods, metric definitions, sources and limitations visible where needed to interpret the result, within the user's chosen layout.
- Use relevant [notices.md](notices.md) wording; a narrow concept answer does not need a long investment disclaimer.

## Working Records and Handoffs

Maintain source and calculation records proportionate to the task in existing notes, tables, workbook comments/formulas, logs or other suitable working artifacts. Direct answers need only their actual evidence and calculation basis. Structured JSON is useful when a downstream system or user asks for it, but this Skill does not require serialization or a named protocol.

For a module handoff, transfer the subject, cutoff, facts with source locators, metric basis, inputs, assumptions, conclusions, constraints, risks, gaps and existing files that the downstream work needs. Identify the responsible final module and order work by dependencies. Do not silently change upstream inputs; version a material change and explain its impact. Record defaults as assumptions instead of presenting them as facts.

## File Delivery

1. Create genuine files in the requested format. Renaming an extension is not conversion. Do not fabricate links or imply that a file was created when it was not.
2. Open or parse the actual file with appropriate tools. Check required content, editability where requested, formulas, references, rendering and layout as applicable.
3. Verify the final saved version after any change. Review evidence from an earlier version does not certify the modified file. Preserve baseline content when the user requests a limited edit.
4. Keep source extracts, model working files, logs and review records internal unless requested or needed for the task. Attach only authorized visible files, and confirm their existence, readability and accessible paths.
5. Review confidentiality, identifiers, hidden sheets, comments, metadata, notes and embedded content relevant to the delivery. Obtain any missing external-distribution approval before sending or publishing.

Use descriptive filenames, preserve requested filenames, and exclude unnecessary personal or account identifiers. Suggested naming: module_project-purpose_YYYYMMDD.ext. This is a convention, not a mandatory filename parser.

## Completion and Limitations

Describe the actual outcome: completed for the requested scope, partial because specified checks/data are missing, or unable to proceed because a required capability/input is unavailable. There is no mandatory status enumeration. Explain the affected conclusion and next verification step; useful scoped output may still be delivered.

Do not claim that a source was independently verified, a model recalculated, a backtest executed, a file rendered or a reviewer approved the final material unless the corresponding action occurred. Passing an arithmetic or format check covers that check's scope; it does not establish all financial semantics or permission to publish.

If a review or tool is genuinely required and unavailable, retain the relevant limitation. Do not manufacture approval or silently switch source, formula or output format to obtain a passed label.
